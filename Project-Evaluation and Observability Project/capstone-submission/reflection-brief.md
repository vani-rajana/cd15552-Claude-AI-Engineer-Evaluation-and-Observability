**2a. Two guarantees.** Paste your discrepancy-run output. Tool use already forces valid JSON, yet the
validator still catches a bad sum. Why are these two different guarantees? Name one error each cannot
catch.

> Output from `02-mortgage-extraction/discrepancy-run.txt`:
> ```json
> "validation": {
>   "consistent": false,
>   "discrepancies": [
>     {
>       "field": "total_monthly_income",
>       "calculated": 9642.17,
>       "stated": 10892.17,
>       "delta": -1250.0
>     }
>   ]
> }
> ```
> **Why these are two different guarantees:**
> - **Schema / Tool Choice Guarantee:** Enforces structural and syntactic conformity (valid JSON formatting, correct keys, and correct data types such as floats or strings).
> - **Deterministic Validator Guarantee:** Enforces semantic and mathematical consistency by executing independent domain arithmetic across extracted fields.
> 
> **Errors each cannot catch:**
> - *Tool Choice cannot catch* an internal math error where the stated total ($10,892.17) deviates from the sum of line items ($9,642.17), because both numbers are valid floating-point values that satisfy the JSON schema.
> - *The Validator cannot catch* structural schema violations (such as missing required fields or unparseable malformed text), because the validator assumes the payload has already been validated into typed Pydantic objects.

**2b. Refusing to fabricate.** Run on a document missing a field. Paste that field's output. Why null
instead of an invented value? Point to the schema choice that allows it.

> From `02-mortgage-extraction/extract-run.txt` (evaluating `fixtures/documents/income_missing_bonus.txt`):
> ```json
> "bonus_monthly": null
> ```
> *(Also null: `commission_monthly: null`, `overtime_monthly: null`, `other_monthly: null`)*.
> 
> **Why null instead of an invented value:**
> In underwriting, silence from a document is distinct from a confirmed zero. If an employee's paystub makes no mention of bonus income, asserting `0.00` constitutes an unsubstantiated claim that downstream loan engines could misinterpret as verified zero-bonus terms. Returning `null` explicitly signals that the document was silent.
> 
> **Schema choice:** In `mortgage_extractor/schema.py`, optional numeric attributes are defined with nullable union types:
> ```json
> "type": ["number", "null"]
> ```
> This schema definition explicitly gives the model the legal syntactic pathway to output `null` without triggering validation rejection.

**2c. Normalization.** Quote one field where the source text and extracted value differ in format
("about 2,400 sq ft" → `2400`). Why normalize at extraction time rather than downstream?

> In `02-mortgage-extraction/extract-run.txt` (from `fixtures/documents/appraisal_informal_sqft.txt`):
> - Extracted value: `"gross_living_area_sqft": 2400`
> - Source document text: `"about 2,400 sq ft"`
> 
> **Why normalize at extraction time:**
> Performing unit and string normalization during extraction establishes a clean, canonical data boundary. All downstream consumers—such as mathematical validators, automated valuation algorithms, routing nodes, and analytical data warehouses—can ingest `gross_living_area_sqft` strictly as a primitive integer. Postponing normalization would force every downstream service to implement custom regex and parsing logic to interpret varied conversational human descriptors.
